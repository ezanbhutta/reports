01 The big picture

Two surfaces, one live database

CSRs log on one app. The CEO/Manager watches on a separate, private console. Both talk to the same Supabase database, so every action a CSR submits appears on the manager's screen instantly.
CSR Logger
Pick name · shift · profile, then log actions all shift. Sees only their own live dashboard.
🔑 Team passcode
writes / reads
Manager Console
Live view of every CSR, shift & profile. Read-only. Not linked from the CSR app.
🔒 Manager passcode (separate)
DB
  Supabase · Postgres + Realtime
One shared store. CSR submits → row inserted → Manager Console updates live (no refresh).

Why it's built this way

  • Self-contained. No sheets, no ClickUp pulls — the CSRs' entries are the only source.
  • Role-separated. Two URLs, two passcodes. CSRs never reach the manager console.
  • Live. Supabase Realtime pushes each new entry to the manager instantly.

06 Step 4 — Close

Checking out

One button ends the shift. It's the only thing that records the check-out time, so the worked hours stay accurate no matter how much editing happened.
CSR keeps logging & editing
check-in time fixed since Start
Press “ Submit shift & check out ”
the one and only check-out trigger
Check-out time stamped (PKT) · shift locked
worked hours = check-out − check-in
Shift summary saved & visible to the manager

The rule, plainly

  • Submit = check-out. Nothing else stamps the time.
  • Re-opening to edit an entry does not move the check-out time.
  • Once submitted, the shift is finalized and rolls into the manager's totals.

Data model notes

  • One session per CSR per shift (name · shift · profile · check-in/out).
  • One activity row per logged action; its fields sit in details.
  • KPI counts = count(activity) group by type — generated, never typed.

Stack & realtime

  • React + Vite + Tailwind on Vercel — two builds (CSR app, Manager console).
  • Supabase Postgres + Realtime + row-level security.
  • CSR submits → row inserted → Realtime pushes it to the console instantly.
